Receive and select samples

Start with Send and receive your first sample to create a matched writer and reader. This guide uses a typed dds::sub::DataReader<T> and shows when to read, take, or select records from its history.

Choose how to access the reader history

Goal Call What happens to the matching records
Inspect records and keep them available reader.read() The reader retains the records and marks them as read. An unread-only filter skips them on later calls.
Consume a batch reader.take() The reader removes the records it returns. Later reads and takes cannot retrieve those same records.
Limit a batch by state, instance, or count reader.select() followed by read() or take() The selector applies the requested filters. The final operation determines whether records are retained or removed.

The direct calls use the reader's default_filter_state(). A new selector starts with its own state filter that matches all sample, view, and instance states. Set the selector's state explicitly when the application needs a narrower selection. See dds::sub::status::DataState for the three state masks.

Diagnose an empty result

An empty read() or take() result can mean no matching records, an allocation failure, or an error from the C library. Use subscription_matched_status().current_count() to confirm a writer is matched. Then send a fresh sample and check the content filter, instance handle, and sample-state mask. For example, an unread-only filter skips a sample after read() marks it as read. See Diagnose a writer and reader that do not exchange data when the endpoints do not match.

With a match and a fresh write, compare the default-state read with an explicit selector that accepts all states. If both are empty, check loss and rejection before assuming the filter is the cause.

Diagnose lost and rejected samples

Read sample_lost_status() to check for losses before delivery. Read sample_rejected_status() to inspect samples the reader rejected and the latest rejection reason. Check last_reason() for a limit on instances, samples, or samples per instance, then compare it with the reader's History and ResourceLimits. last_instance_handle() identifies the instance in the last rejection. Keep one status snapshot if several parts of the application need its change count.

Follow one keyed instance

Send a sample for a new key. Look at its instance handle and view state. A read marks the returned record as read. A take removes it. Then dispose the instance as shown in Detect a disposed instance and check SampleInfo::valid() before accessing its payload.

Read rank() for the returned batch. See Inspect ranks across instance generations for how the ranks change across two generations.

Process a loaned batch

Reader history and sample loan lifetime

Use the Hello::Msg DataReader from the keyed tutorial. Its topic type contains userId and message fields.

void print_next_batch(dds::sub::DataReader<Hello::Msg>& reader)
{
const auto samples = reader.take();
for (const auto& sample : samples)
{
if (!sample.info().valid())
continue;
std::cout << sample.data().userId << ' ' << sample.data().message << '\n';
}
}

Check SampleInfo::valid() before reading the payload. An instance state change can arrive without a payload.

Keep the dds::sub::LoanedSamples collection alive while using a sample reference, iterator, or a pointer stored in a payload. Copy the fields your application needs into owned storage before the collection is destroyed. For example, construct a std::string from a valid Hello::Msg::message while the loan is alive if the application needs that text later.

Select a batch without changing the default filter

DataReader selection and returned samples

Use a reader on a keyed topic with a message field, such as Hello::Msg in the keyed example. Pass a handle obtained from that reader to take up to eight unread records for one known instance. Checking for a nil handle avoids selecting all instances when a lookup did not find the requested key.

void print_unread_instance(dds::sub::DataReader<Hello::Msg>& reader, const dds::core::InstanceHandle& handle)
{
if (handle.is_nil())
return;
const dds::sub::status::DataState unread(dds::sub::status::SampleState::not_read());
const auto samples = reader.select().instance(handle).state(unread).max_samples(8).take();
for (const auto& sample : samples)
{
if (!sample.info().valid())
continue;
std::cout << sample.data().message << '\n';
}
}

Use lookup_instance() for a known key. sample.info().instance_handle() identifies the instance of an incoming record.

To filter on values in the payload, create the reader on a content-filtered topic. The Content-filtered subscriber shows a reader that accepts samples with userId > 5.

Choose a destination for copied records

The iterator overloads write records and metadata into application-provided storage. A call with buffer.begin() and a positive count uses existing writable slots. Ensure the buffer has at least that many slots before calling. A call with std::back_inserter(buffer) appends to a growable container and may allocate. Both forms return the number of records written.

Use a topic type whose copy owns its payload fields. These functions use IdlExample::Message from Generate and use C++ code from IDL, which contains one integer. Both functions use the reader's default state filter.

#include <gurumdds/dds.hpp>
#include <MessageTypeSupport.hpp>
#include <array>
#include <cstdint>
#include <iterator>
#include <vector>
using MessageSample = dds::sub::Sample<IdlExample::Message, dds::sub::SampleInfo>;
std::uint32_t read_into_buffer(dds::sub::DataReader<IdlExample::Message>& reader, std::array<MessageSample, 8>& buffer)
{
return reader.read(buffer.begin(), static_cast<std::uint32_t>(buffer.size()));
}
std::uint32_t append_taken_records(dds::sub::DataReader<IdlExample::Message>& reader, std::vector<MessageSample>& buffer)
{
return reader.take(std::back_inserter(buffer));
}

If the topic type contains borrowed pointers, use the loan and copy the needed values into owned fields while it is alive. Copying the record with an iterator uses the topic type's C++ copy semantics.

Set max_samples(n) on the selector itself when copying a bounded selection. The selector's forward-iterator overload uses this setting. For fixed-capacity storage, choose a positive limit no larger than the number of writable slots.

Warning
Iterator-based take() removes records from history before copying. If assignment or insertion throws, the destination may contain only part of the batch, and the removed records stay out of history.

Follow an instance through disposal and unregister

Build the example_cpp_helloworld_keyed_subscriber and example_cpp_helloworld_keyed_publisher targets with the example build from Send and receive your first sample. Start the subscriber first. Both programs use domain 79, topic HelloWorld, and a type keyed by userId.

The keyed publisher writes three keys. For userId 1, it registers and writes hello, explicitly disposes the instance, writes world for the same key, and unregisters that key. The keyed subscriber reads batches of up to eight unread records and prints the key and instance state.

Publisher action for key 1 What to look for on the subscriber
Write hello ALIVE with the value hello
Dispose the instance NOT_ALIVE_DISPOSED
Write world ALIVE with the value world
Unregister the last writer for the key NOT_ALIVE_NO_WRITERS
Instance state changes for one key
Instance state and Reader purge delays

This sequence assumes the example is the only writer for that key and the subscriber reads while the publisher is running. The publisher disables automatic disposal on unregister so the final unregister can be observed as loss of the last writer. With automatic disposal enabled, unregistering also requests disposal.

The subscriber gets the key for a state notification through key_value() using the record's instance_handle(). It reads payload fields only when valid() returns true. After observing NOT_ALIVE_NO_WRITERS, it uses a selector to take records still retained for the saved handle. Check Diagnose a writer and reader that do not exchange data if the subscriber receives no records.
