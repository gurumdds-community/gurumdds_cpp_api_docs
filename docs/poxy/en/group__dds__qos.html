QoS policy summary

These are factory defaults. Configuration and publisher or subscriber defaults can override them. Read the QoS on the entity to check its settings.

Matching refers to compatibility between a DataWriter and DataReader. Configure DataWriter policies when you create the writer.

Select the source before editing a policy. Changing a parent's defaults affects future children created without explicit QoS.

Diagnose a writer and reader that do not exchange data

Keep one writer and one reader running while DDS discovers them. See Send and receive your first sample for the build and run commands.

Check the endpoint configuration

  1. Compare the participants' domain IDs. The publisher and subscriber must join the same DDS domain. Check that both processes are running and can discover each other on the intended network.
  2. Check the topic names, registered types, field definitions, and keys on both sides.
  3. Compare Partition on the Publisher and Subscriber. The lists must share a matching name. An empty list uses the default partition with an empty name.
  4. Compare the endpoint QoS. The writer offers a service level and the reader requests one. Use the match and incompatible QoS counters below to see whether DDS accepted the pairing.
  5. If the endpoints are matched, write a fresh sample and check which samples the reader selects. A content filter can exclude the sample, and a state or instance filter can keep it out of a particular read or take. Check sample.info().valid() before accessing its payload. See Receive and select samples for help choosing a receive operation.

Print topic.name() and topic.type_name() in both processes. If the topic names match, compare the registered type and the IDL fields and keys separately.

Diagnose a two-host test

Run the two-process pair on one host first. On each host, verify that the executable loads the intended SDK and binding. Then run one endpoint per host. With zero matches, check the configured interfaces and network rules for DDS discovery. After a match, send a fresh sample and inspect the reader filter and status.

Compare the relevant QoS policies

PolicyConfigure onWhat to compare
PartitionPublisher and SubscriberAt least one matching partition name.
ReliabilityDataWriter and DataReaderA RELIABLE reader requires a RELIABLE writer. A BEST_EFFORT reader can match either kind.
DurabilityDataWriter and DataReaderA TRANSIENT_LOCAL reader requires a TRANSIENT_LOCAL writer. A VOLATILE reader can match either kind.
DeadlineDataWriter and DataReaderThe offered update period must be at most the requested period.
HistoryDataWriter and DataReaderControls retention per instance. Each endpoint can use its own history kind and depth.

Set the intended policies explicitly when creating the endpoints for this check. Recreate a reader or writer to change its Reliability, Durability, or History. Use TRANSIENT_LOCAL on both sides and configure retention to deliver retained samples to a reader that matches after the write. See Quality of Service for policy details.

Read the status snapshots

On the reader, inspect subscription_matched_status().current_count(). On the writer, use publication_matched_status().current_count(). A positive value means the endpoint has at least one current match. A cumulative match count can stay positive after the other endpoint has exited.

Inspect requested_incompatible_qos_status() on the reader and offered_incompatible_qos_staus() on the writer. In a fresh test, a positive total_count() shows that DDS detected an incompatible QoS setting. last_policy_id() identifies the latest reported policy. If the count stays zero, continue checking discovery, topic, and partition settings. Keep the returned snapshot if more than one component needs the change counters. Reading these statuses resets their change counters and clears their corresponding changed flags on the entity.

wait_for_acknowledgments() applies to published samples. A return without an exception can occur even when there is no matched reliable reader, so use the match status to check for a peer. For exception handling and calls that report failures differently, see Errors and threading.

Reproduce and fix a Reliability mismatch

In the Hello World publisher, replace the writer declaration with the following lines. These lines use the existing pub and topic variables.

dds::pub::qos::DataWriterQos writer_qos;
writer_qos << dds::core::policy::Reliability::BestEffort();
dds::pub::DataWriter<HelloWorldData_Msg> dw(pub, topic, writer_qos);

In the subscriber, replace the reader declaration with the following lines.

dds::sub::qos::DataReaderQos reader_qos;
reader_qos << dds::core::policy::Reliability::Reliable(dds::core::Duration::from_millisecs(100));
dds::sub::DataReader<HelloWorldData_Msg> dr(sub, topic, reader_qos);

Add <chrono> and <thread> to both source files. Keep the publisher alive for this check by adding std::this_thread::sleep_for(std::chrono::seconds(10)); after its write. In the subscriber, use the following diagnostic loop in place of its open-ended receive loop. Start the subscriber and then the publisher within the five-second diagnostic window.

const auto end = std::chrono::steady_clock::now() + std::chrono::seconds(5);
bool has_reported = false;
while (std::chrono::steady_clock::now() < end)
{
    if (dr.subscription_matched_status().current_count() > 0)
    {
        std::cout << "Reader matched a writer\n";
        has_reported = true;
        break;
    }

    const auto incompatible = dr.requested_incompatible_qos_status();
    if (incompatible.total_count() > 0)
    {
        const auto policy = incompatible.last_policy_id();
        if (policy == dds::core::policy::policy_id<dds::core::policy::Reliability>::value)
            std::cout << "Reliability mismatch\n";
        else
            std::cout << "Incompatible QoS policy " << policy << '\n';

        has_reported = true;
        break;
    }

    std::this_thread::sleep_for(std::chrono::milliseconds(100));
}

if (!has_reported)
    std::cout << "No match or incompatible QoS reported within five seconds\n";

With the best-effort writer and reliable reader, expect Reliability mismatch after discovery. Replace BestEffort() in the publisher with Reliable(dds::core::Duration::from_millisecs(100)), rebuild, and restart both processes. With the other settings unchanged, expect Reader matched a writer. To verify data reception, restore the receive loop from the Hello World subscriber and run it with the compatible writer.
