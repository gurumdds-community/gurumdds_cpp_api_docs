Errors and threading

Check the return value before retrying. Handle the exceptions documented for each operation.

Handling DDS exceptions

Operations that translate native errors throw types derived from dds::core::Exception. Catch specific exceptions when you can act on them. Catch the base type where you report failures to the caller.

  • dds::core::InvalidArgumentError and dds::core::PreconditionNotMetError indicate that the application should check the arguments, entity state, or call order.
  • dds::core::NotEnabledError indicates that the operation requires an enabled entity.
  • dds::core::InconsistentPolicyError indicates that the application should check the policy combination.
  • dds::core::ImmutablePolicyError indicates that the setter rejected a change. Set creation-time policies such as Reliability and History when creating the entity. To change them, recreate the entity with the desired QoS.
  • dds::core::TimeoutError and dds::core::OutOfResourcesError indicate that the requested operation could not complete in time or DDS could not obtain resources. The exact condition depends on the function.

The following function takes an enabled, reliable writer and waits for pending acknowledgments for up to 250 ms. It handles a timeout and leaves other failures for the caller to handle.

#include <gurumdds/dds.hpp>

template <typename T>
bool wait_for_ack(dds::pub::DataWriter<T>& writer)
{
    try
    {
        writer.wait_for_acknowledgments(dds::core::Duration::from_millisecs(250));

        return true;
    }
    catch (const dds::core::TimeoutError&)
    {
        return false;
    }
}

An acknowledgment wait can succeed with no reliable reader matched. Check the matching status in Diagnose a writer and reader that do not exchange data to confirm peers.

A wait on dds::core::cond::TWaitSet uses a different result contract. It reports triggered conditions through its returned sequence, and an empty sequence does not identify the reason why no condition was reported.

Coordinating a WaitSet

Use one waiting thread per WaitSet. Attach or detach conditions before waiting. Keep the WaitSet and condition owners alive until the wait returns. A finite timeout lets the thread check for shutdown. For each returned condition, read its entity status or take the matching samples.

Working with listeners

The application owns the listener. Keep it alive while registered and until its callbacks finish. Synchronize state shared with other threads. A callback can hand longer work to an application worker. Copy the worker’s sample data before releasing LoanedSamples.

On the subscription side, an enabled dds::sub::SubscriberListener::on_data_on_readers() takes precedence over a reader's data-available callback. The subscriber callback can call dds::sub::TSubscriber::notify_datareaders() to schedule reader callbacks for eligible readers. See Receive and select samples for sample access and loan lifetimes.

Choose the listener scope and release it

Use a typed DataReader or DataWriter listener for one endpoint. Use the Subscriber listener for aggregate data availability. A parent listener receives the callback types and status mask supported by that parent.

During shutdown, stop handing off new work. Deregister through the entity's listener setter where supported. Let running callbacks finish, finish work that uses loaned samples, then release the loan owners and listener.
